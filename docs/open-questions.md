All figures: Linux, one core of a shared 4-vCPU VM, release build, CPU time with `os.clock` and peak memory from `VmHWM` of `/proc/self/status`; repeat them with `lua docs/spikes/OQ-52/hostile-input.lua time|memory|literal` (also on dedicated hardware). **(1) Failure path of the native decoder, open.** When yyjson rejects a text, the binding parses the whole text again with the pure-Lua decoder to name the reason and the offset. A 16 MiB array of ones, `[1,1,...,1]`, decodes in 1.4 s; the same text with a trailing comma, `[1,1,...,1,]`, is rejected after 6.2 s, and with an invalid byte at the end after 7.0 s: a hostile body costs about 5 times a valid one on the single-threaded reactor, and the sender picks the path (the HTTP layer applies a smaller body limit of its own, OQ-49). Options: (a) accept and document; (b) lower the default `max_size` (for example 1 MiB); (c) read the error of yyjson (`yyjson_read_err`: a code, a message and a byte position) and return it, with the line and column computed from the position, instead of the Lua pass; the reason and message become yyjson's generic ones (`unexpected character`, `invalid number`, `unexpected end`) and the reference decoder's wording must follow so that both backends say the same; only what yyjson accepts and the codec rejects (a duplicate member name, a lone surrogate) would still need the Lua pass; (d) the full, reference-worded diagnosis only when asked for (a `decode` option, set by a development configuration of the application), the fast native error otherwise. **(2) Memory before the depth check, open.** yyjson allocates a node for every `[` before the codec compares the nesting with `max_depth`: a text of 16 MiB made only of `[` (16 777 216 brackets) takes the process from 18 MB to 291 MB of resident memory (about 17 bytes of memory per byte of input) and 1.7 s before `depth_limit` is returned. Solution: a pre-scan in C that counts brackets outside strings and rejects the text at the first bracket beyond `max_depth`, before yyjson runs (one pass over the text, a few tens of milliseconds for 16 MiB, no allocation, the exact offset); lowering `max_size` also bounds it. **(3) Very long number literals, open.** The native decoder (yyjson) is wrong, by one unit in the last place, on an exact tie written with a very long tail: the literal `1.00000000000000011102230246251565404236316680908203125` (exactly 1 + 2^-53, the midpoint between `1.0` and `1.0000000000000002`) followed by 715 or more zeros decodes to `1.0000000000000002` natively and to `1.0` with the reference decoder (round half to even gives `1.0`, which is right); yyjson keeps a limited number of digits. A literal of that kind never occurs in practice; options: cap the length of a number literal (for example 1 000 characters) or leave it. **(4) Encoder cost, accepted for the first release (owner, 2026-10-20):** the encoder keeps the entries of a table before it checks `max_size` and expands shared substructure (a value of 150 levels in which every level refers to the same child twice took 7.5 s to reach `size_limit`); only values built by the application reach it. **Decided (owner, 2026-10-20):** a text or value nested beyond 1000 levels is an error (`depth_limit`), never a crash or a fallback: `max_depth` is at most 1000 for `decode` and `encode` alike, with the same defaults and bounds for `max_size`. The echo of input bytes in error messages is fixed (excerpts of at most 40 bytes, control characters escaped). | `json`, `http` |
| OQ-50 | decision | `schema`, `kernel`, typed route bodies (owner idea, 2026-10-20): a route declares the type it expects, and the handler receives the request body already decoded and built as an instance of that class instead of decoding it by hand. Pipeline: `http` collects the body under its own limit, `json.decode` gives plain tables, `schema` validates and coerces against the route's schema (JSON Pointer error paths, RFC 9457 problem details), and builds the instance when the schema is tied to a class. `json` stays unaware of classes and schemas (layer 1), and `json.decode` and `json.encode` stay available for manual use.
