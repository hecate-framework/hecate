# Documentation

Status: specification; [ADR 0012](../adr/0012-website-generator.md) (Accepted: site generated by
`hecate.doc` with an MDN-like theme),
[ADR 0022](../adr/0022-doc-dependencies.md) (Accepted: dependencies of the generator),
[ADR 0013](../adr/0013-english-code-multilingual-documentation.md) (Accepted),
[ADR 0032](../adr/0032-unicode-normalisation-packages.md) and

## Two kinds of documentation

1. **Engineering documentation** (`docs/`): for contributors and agents. English only.
2. **Public website** (`website/`): for users. English source, translated.

Hosted at <https://hecate.theandre.dev> (provisional domain), deployed from `main` by
`website.yml`.

## Website structure (Diátaxis)

| Section | Purpose | Examples |
|---|---|---|
| Tutorials | learning by doing, reproducible verbatim | "Your first API", "A CRUD API with PostgreSQL" |
| How-to guides | solving one task | "Paginate a collection", "Deploy with Docker", "Add JWT authentication" |
| Reference | exhaustive, mostly generated | every package, class, function, CLI command, configuration key, error code |
| Explanation | concepts and rationale | concurrency model, suspension points, object model, data mapper, contracts |

Plus: migration guides between minor versions, glossary (public version of
`docs/glossary.md`), correspondence tables (relational algebra ↔ SQL; Hecate ↔ FastAPI /
Symfony / Express vocabulary), changelog, compatibility matrix.

The full site map is in [`website/OUTLINE.md`](../../website/OUTLINE.md).

## Generated reference

- Source: LuaLS annotations (`lua-language-server --doc` export, JSON) + route, schema
  and configuration metadata from the packages.
- Produced by `hecate doc` (Phase 3; the scripts of `packages/doc/bin/` before that, wrapped by `gen-reference`) into
  `website/user/en/reference/` as Markdown. Generated pages are never edited by hand; they
  carry a header comment saying so.
- The error codes page (`reference/error-codes.md`, every error class of ADR 0018 with its code, parent and
  `context.reason` values) and the configuration keys page (`reference/configuration-keys.md`) are produced by the
  `gen-error-codes` and `gen-config-reference` tasks (automation.md), from the sources read as files; like the code
  reference they are git-ignored and generated by `website.yml` before the site build.
- Translations of generated pages translate only the prose parts (summaries,
  descriptions) through translation files keyed by symbol, not whole pages.

## Theme

One original Hecate theme for the website and for user projects (ADR 0012): MIT-licensed,
light and dark modes, WCAG 2.2 AA. No code or assets from Lua Web Docs (Tailwind UI
licence).

Owner direction of 2026-10-13 (ADR 0012): `hecate.doc` is our own Lua 5.5
generator with a VitePress-like presentation and strict respect of the Hecate brand kit
(`tokens.json`, logo lockups, STIX Two / Fira Sans / Fira Code, nearly square corners, no
gradients or glows, the name never capitalised, earth as the single accent). Page chrome:

- top bar: logo, section links, search, locale switch, theme toggle, repository link,
  menu button on small screens;
- left sidebar (computed from the page tree or configured per section) and a right-hand
  "On this page" outline;
- previous/next cards, edit-this-page link, last-updated date, "written for hecate x.y and
  Lua 5.5" line;
- callouts (the five GFM alerts NOTE, TIP, IMPORTANT, WARNING and CAUTION), code blocks with a language label
  and a copy button, tables, task lists;
- search: one index per locale, written as a script file (`assets/search-<locale>.js`, loaded with a script element, so
  that it works from the file system) and queried by about 150 lines of vanilla JavaScript;
- diagrams: a fenced block whose info string is `mermaid` stays a code block, and on a page that holds one the
  theme loads a vendored copy of `mermaid.js` (no CDN) that draws it in the reader's browser, in the brand
  colours of the light or the dark theme ([ADR 0033](../adr/0033-vendored-browser-libraries.md), Accepted;
  OQ-128). The library and its initialiser are loaded, and written to the output, only for pages with a diagram;
  without JavaScript the source stays readable.

Implementation and conventions: [`packages/doc`](../../packages/doc/README.md); open
choices OQ-33 to OQ-38. Build, one site per tree (bootstrap runner until `hecate doc build`):
`lua packages/doc/bin/build.lua website/user --config website/site.lua --reference --internals-into website/maintainer --audience user --out website/dist/user --strict`
then `lua packages/doc/bin/build.lua website/maintainer --config website/site.lua --audience maintainer --out website/dist/maintainer --strict`
(`.github/workflows/website.yml` is the reference).

### Manual check on a narrow viewport

Before changing the navigation of the theme, build the site and open it in a browser at 375 px
wide (device mode). With the sidebar open ("Menu" in the local bar) and with the header panel open
(hamburger): a long menu scrolls inside its own container, the page behind does not move, and the
last entry is reachable with the address bar visible. `ThemeTest` guards the CSS and script rules
behind this behaviour.

## Reference page template (MDN-like)

Inspired by Lua Web Docs (<https://luadocs.com>, "like MDN, but for Lua"). Every
reference page for a class or function follows the same sections, in this order:

1. One-sentence summary.
2. Syntax (signature, LuaLS-style types).
3. Parameters and return values (including `nil` for expected absence, ADR 0018).
4. Errors raised (classes and codes).
5. Whether it may suspend (`---@async`) and on which operations.
6. Examples (tested files, runnable when possible).
7. Specifications and standards implemented (RFC sections).
8. Compatibility: Hecate version introduced, Lua versions supported.
9. See also.

## Runnable examples (WebAssembly, OQ-11 and OQ-39)

Pure-Lua packages (`core`, `schema`, `router`, `query`) could run in the browser if Lua
5.5 is compiled to WebAssembly, letting readers edit and run examples on the page.
Anything depending on the reactor (libuv) cannot run in the browser and keeps static,
tested examples. The OQ-11 spike decides.

## Content conventions (owner decision 2026-10-13, OQ-35)

- **Page title.** The title of a page is the single `#` heading of its body. That keeps the
  Markdown readable on GitHub and satisfies markdownlint MD025 and MD041. The generator
  renders that heading as the page's only `<h1>` and does not repeat it.
- **Front matter `title`** is optional and overrides only the label used in navigation,
  previous/next cards, search results and the HTML `<title>` (short label, SEO wording). It
  never replaces the visible heading. Without a body heading, `title` is displayed as the
  heading; without both, the page id is humanised and a problem is reported.
- **Code samples** are included from tested files from the start (rule below), never typed
  into the page.
- **Reference generation.** Every module table carries a `---@class` annotation so that the
  `lua-language-server --doc` export contains its functions; `hecate.doc` does not parse
  annotations itself. Parameters and returns are described in the standard form
  `---@param name type description` and `---@return type name description`.

## Static output (OQ-148)

Owner decision of 2026-11-24: `hecate doc` produces static files only, like Javadoc, with no server, no `serve` command and
no option for the mode. A built site opens from the file system (`file://`) and from any static host, under any path.

- **Relative links.** A page links to the other pages and to its assets (stylesheet, scripts, fonts, logo, favicon,
  Mermaid, the files of `public/`, the files next to the pages) by a path relative to the file it is written in
  (`../../../assets/theme.css`), never by a path that starts with `/`. A link to a page names its file
  (`../b/index.html`): a browser lists a directory that it opens from the file system. The stylesheets use relative
  `url(...)`. A link written in Markdown is resolved to a relative one; one that starts with `/` names a path below the
  root of the site.
- **`base_path` and `site_origin`** build no link. They give the absolute addresses of the site: the canonical and alternate
  links, `sitemap.xml`, `llms.txt` and `llms-full.txt`, the canonical link of the root redirect and the links of `404.html`
  when `site_origin` is set (a host serves `404.html` for any address, so a relative link would break there; without
  `site_origin` the links of `404.html` are relative to the root). `base_path` stays a validated option (an absolute path,
  default `/`), so that existing `site.lua` files keep working; `Page.url` is the public address
  `<base_path><locale>/<page path>/`.
- **Search index.** A script file per locale, `assets/search-<locale>.js`, one assignment to
  `window.hecateDocSearchIndex[<locale>]`; the documents are addressed by a path below the root of the site
  (`en/guide/index.html#section`) and `theme.js` prefixes the path from the page to the root (`root` of the `doc-config`
  element of the page). The script is added when the search opens for the first time. A `fetch` of a JSON file is refused
  by browsers on `file://`, a script is not. The content is deterministic.
- **Test.** The files written by a build are read back, and every local `href`, `src`, `url(...)` and meta refresh of every
  page and stylesheet must resolve, from the directory of its own file, to a file of the output; no root-relative local
  reference may remain.

## Writing rules

- Every page states the Hecate version it was written for and the Lua version.
- Every code sample is a tested file under `packages/<name>/examples/` or
  `examples/`, included by reference, so samples cannot rot. The renderer has no include
  mechanism yet: a page writes `<!-- example: packages/<name>/examples/<file>.lua -->` on a line of
  its own, then a fenced block holding the exact content of that file, and `check-docs-examples`
  fails when the block differs or the file is missing. A snippet of a few lines may stay inline.
- Vocabulary from the glossary; first occurrence of a term links to the glossary.
- Short sentences, active voice, second person in tutorials and how-tos.
- Follow the writing style below.

## Writing style

Owner decision, 2026-11-13. The public pages are written after the manner of *Programming in Lua* (Roberto
Ierusalimschy): a patient teacher who introduces one thing at a time, shows it at once, and never trades accuracy for
ease. Readability comes from the order and the pace of the text, not from looser words. The rules apply to every page
of `website/user/en/`; the engineering documents of `docs/` keep their denser, reference style.

1. **One idea per paragraph.** A paragraph states one idea and stops. When a paragraph needs "also", "in addition" or
   a second topic sentence, split it. Three to five sentences is a good length; a one-sentence paragraph is fine.
2. **Example right after the concept.** Each new concept is followed at once by a short example: a few lines inline,
   or a tested example file (`<!-- example: ... -->`). The example comes before the details, the options and the
   exceptions, which follow it. Never pile several concepts up before the first example.
3. **Recall a term the first time a page uses it.** The first occurrence of a glossary term on a page links to the
   glossary and is followed by a brief reminder of what it means, in a clause or a short sentence ("a filter, an
   object that wraps the action of a route, ..."). Do not assume the reader came from another page.
4. **Short sentences, lower density.** Aim for sentences under about 25 words. One clause per idea; prefer two
   sentences to a semicolon. Lists of more than three items become a bulleted list or a table. Leave room: a page
   that covers less, clearly, is better than one that covers everything in packed sentences.
5. **The precise term and the exact claim, always.** A simpler sentence never replaces a glossary term by a vaguer
   word, never drops a condition that makes the claim true ("at boot", "on the same reactor", "since 0.x"), and never
   rounds a limit or a default. When the exact claim is long, give it its own sentence or list item rather than
   simplifying it.
6. **Lead with the purpose.** A section opens with what the reader can do with the thing or why it exists, then how
   it works. Rationale and history go last, or to an explanation page.
7. **Move from the common case to the rare one.** Show the usual use first; edge cases, limits and "not available
   yet" come after, each in its own paragraph or under its own heading.

A short illustration of rules 1 to 3:

> Too dense: *Filters, composed once at boot into a chain of responsibility over the action, may pass, short-circuit
> or post-process, and errors they raise go through the guard like the action's.*
>
> Readable: *A [filter](../../website/user/en/reference/glossary.md) wraps the action of a route: it sees the request
> before the action and the result after it. Here is the smallest filter, one that passes the request on:* (example)
> *A filter can also stop the request before the action, by returning a result without calling `next`.*

## Code examples

Owner request, 2026-11-12. Two rules apply to every code example: the files under `packages/*/examples/` and
`examples/`, and the Lua blocks of the website pages.

1. **Comment width.** No line that holds a comment is longer than 80 characters, counting the indentation and any
   code before the comment. Code lines without a comment may be longer and are not broken unnaturally to fit. A
   line is exempted only when the line just above it is a comment holding `check-examples: allow-long-comment`.
   `check-examples` enforces this rule. It runs in the `docs-checks` and static-check jobs of `ci.yml`. A block that
   copies an example file (`<!-- example: ... -->`) is checked through that file.
2. **Output placement.** What a line makes the reader see is written in a `-- Prints:` block directly under that
   line, never gathered at the end of the example. The block starts with `-- Prints: <first line>` and continues
   on the comment lines `-- <next line>` that follow it. One block holds the output of one line. Only the rest of
   the printing statement may stand between the line and its block: the remaining arguments of a call that spans
   several lines, or closing lines such as `end)`. Inside a function, the block goes inside it, indented. Examples
   write through `print` only (`io.write` and `io.stdout` are refused). A server example that never returns ends
   with `-- Answers: <text>` instead.

```lua
local ok, value = schema.integer():validate(42)
print(ok, value)
-- Prints: true	42
```

The examples tests of every package run their examples through one shared runner, `tools/harness/examples.lua`. It
attributes each `print` to the line of the example that is running and fails when the output is missing, different,
gathered into another line's block, or separated from its line. A `print` inside a helper function counts at the
helper's line, so examples print inline. Every phase gate checks both rules on the examples of its phase
(`docs/roadmap.md`, "Phase gates").

## Translations

- Locales: `en` (source), `fr` (first), more by contribution.
- `website/user/<locale>/` mirrors `website/user/en/`, and the same for `website/maintainer/`.
- Each translated page records the source revision it translates (front matter
  `source_revision`); `check-translations` flags stale pages.
- Untranslated pages fall back to English with a visible notice.

## LLM-facing documentation

- `llms.txt` at the repository root is curated by hand (`gen-llms-txt` keeps its package list). The site builder
  writes `llms.txt` and `llms-full.txt` at the root of a site (llmstxt.org) only when the site configuration says
  `generate_llms_txt = true`; the default is off, so a project publishes nothing for language models unless it asks. `llms.txt` has
  the site title and description, then one link per published page with the `description` of its front matter,
  grouped by top-level section in navigation order (pages at the root first); `llms-full.txt` concatenates the
  Markdown of the same pages, each after a `Source:` line. Only the pages of the tree of the site appear (a page of the
  other audience is in the other site, OQ-144) and only the default locale is written. A file of `public/`
  with the same name fails the build when the key is on. The Hecate website turns it on. The output is
  deterministic.
- Every reference page has a stable anchor per symbol.

## Documentation of a project (audiences)

Documentation has two audiences, a second axis next to Diátaxis (which sorts pages by what they do
for the reader, not by who the reader is; [OQ-144](../open-questions.md), owner remarks of 2026-11-17):

- **user documentation**: build, run and operate an application on the public API, with the concepts
  and the public extension points that help to do so;
- **maintainer documentation**: change Hecate, or the project itself: architecture, ADRs, internals,
  CI and release, the reference of `*.internal` modules.

`hecate doc build` on a project produces a static site that is the project team's own documentation:
the guides the project writes, the configuration reference, and the code reference from the
project's annotations. `hecate.doc` serves maintainers by default (owner decision of 2026-11-18): the
public output of a project is a request (`audiences`), not a default.

The two audiences are **two different websites** (owner decision of 2026-11-21, OQ-144): two content trees in the
sources and two output directories, so that they share no page id (a page id is one file, so one `index.md` can be the
home of one site only) and no static file.

- **Layout.** One content tree per audience, `<guides_dir>/<audience>/<locale>/...` (`user`, `maintainer`), with its own
  `public/` at `<guides_dir>/<audience>/public/`, next to the locale directories as in a plain tree: a tree can be moved,
  built or deleted whole, and the sites never share a static file. The site configuration is one file for the project,
  `<guides_dir>/site.lua`; title, locales, theme and every other key apply to every audience site (per-audience overrides are
  out of scope).
- **Each tree is a plain site.** It is built by the plain builder (`hecate.doc.build`, class `Site`), exactly like the tree of
  the Hecate website, into `<output_dir>/<audience>/`: its own pages, navigation, search index, sitemap, `llms.txt` and
  `llms-full.txt`, `404.html` and theme files, with the public address `<base_path><audience>/` (canonical links, sitemap; the links of the pages are relative). A page of one tree is in no file
  of the other site. `<output_dir>/` holds a marker file and a redirect to the first site built. The builder knows no
  audience: there is no `audience` front matter key (a page that carries it is a `BuildError` naming the file and this layout),
  and `audiences`, `default_audience` and `audience_sites` are no keys of `site.lua` (a `ConfigurationError` says what
  replaced them); there is no merged site.
- **Which sites are built.** The option `audiences` of `generate_project_documentation` lists the trees to build; the
  default is `{ "maintainer" }`. A tree that is not listed is not built and is no error; a listed tree that does not exist
  is a problem with the file to add (`add docs/user/en/index.md`), an error under `fail_on_problems`. Each tree needs its
  own home page (`index.md` of the default locale): its absence is a problem of that tree, and it can be satisfied.
- **Generated pages go to the right tree.** The configuration reference is a page of the `maintainer` tree (written only when
  `maintainer` is built). The code reference lists public symbols in the `user` tree; the pages of `*.internal` modules and of
  classes that LuaLS reports as `private` or `package` go to the `maintainer` tree, and are generated only when it is
  built. With one tree built, the whole code reference goes into it. With both, the pages of one tree never link to the
  other and the module page lists only the classes of its own tree: each tree is self-contained. The licences page goes to
  the `maintainer` tree unless `licences_page.audience` names another listed tree. A member (field or method) that is
  `private`, `protected` or `package`, or whose name starts with `_`, is never listed: a member is a part of a class page,
  not a page. Stale generated pages and the generated-page marker rules apply per tree.
- **Links between the two sites** are ordinary links that the builder cannot check. Write an absolute URL, or a relative
  link that the browser reads from the file of the page (`../../../../user/en/guide/index.html` from `guide/a.md` of the site
  written to `maintainer/`, which opens from the file system as well). The builder leaves a relative link that climbs two levels or more above the locale directory, out of the tree,
  as written and reports no problem; a link that climbs to the content root only is still a problem, as is a broken link inside
  the tree. A switcher between the sites is not built (OQ-144, open).
- Files of the guides are read defensively and written portably as for every tree (symbolic links, depth, entries,
  portable names): see the items below, which hold per tree.
- The configuration reference never prints the default of a secret key (`[redacted]` in its place), nor its
  enumeration, constant or pattern. The schema is the single source (`Configuration:schema()` marks the secrets of
  `hecate.config` `writeOnly: true`): a row is a secret when its schema, or any subschema reachable from it through
  `$ref`, `allOf`, `anyOf`, `oneOf`, `if`/`then`/`else`, `items`, `prefixItems`, `properties`, `additionalProperties`,
  `patternProperties` and the like, says `writeOnly: true` or `format: "password"`, or when it lies below an object
  that does. A default that may hold a secret in any part is redacted whole, whatever the shape (an array, an object cut
  by the depth limit or by a recursion); an unresolvable reference and a search over a huge schema answer "secret".
  Every cell of the table is escaped text: a number is written only when it is finite, and a value that is neither text
  nor a finite number is left out (it would print an address). The application (`application`, a
  `hecate.kernel.Application`, duck-typed on `configuration_schema()`, so that `doc` does not depend on `kernel`)
  is the single source: it returns the schema alone. A project without a Hecate
  application has no configuration to document, so there is no option for a hand-passed schema or secrets.
  The only input of guides is the directory `guides_dir`: there is no option that gives guides as in-memory text
  (owner decision 2026-11-18, OQ-143).
- The generation is `hecate.doc.generate_project_documentation(options)`, distinct from the plain site builder
  `hecate.doc.build`. Its path options are named by what they are (`_dir` a directory, `_path` a file) and have
  defaults from the conventional project layout, relative to `project_dir`: `sources_dir = "src"`,
  `guides_dir = "docs"`, `output_dir = "docs/dist"`, `site_configuration_path = "<guides_dir>/site.lua"`,
  `rocks_tree_dir = "lua_modules"` (the layout of `developer-experience.md` specifies `src/`, `config/`,
  `tests/` and `lua_modules/` but no documentation directory: OQ-143). Like `package.json`, `hecate.project.lua`
  will hold a `doc` section with these options, filled with the defaults by `hecate new` and read by
  `hecate doc build` (roadmap, item `cli`).
- The third-party licences page (`generate_project_documentation` option `licences_page`, off by default,
  `maintainer` by default): the rocks of an installed tree read as files (name, version, declared licence, licence text,
  dependencies resolved transitively and sorted) and what the generated site bundles, with the licence
  texts of the theme. A rockspec is data: it is parsed without being run (no call, `..`, loop or loader
  accepted; an empty environment, an instruction limit and a limit of memory growth for the rest), and no `luarocks`
  process runs.
- Names of files are portable (owner decision of 2026-11-19). One check, `portable_name`, applies to page ids, the files
  next to the guides, the files of `public/` and the files `logo_path`, `favicon_path` and `stylesheet_path` name: the
  naming rules of Windows for every segment (reserved device names, reserved characters, trailing dot or space),
  Normalization Form C, and a case-fold key that must be unique over the pages, the files and `public/` together
  (and a path may not be a file for one source and a directory for another), because macOS and Windows file systems are
  case-insensitive; a `BuildError` before anything is written. The fold is the Unicode simple case folding for Latin,
  Greek, Cyrillic, Armenian and fullwidth letters (OQ-145 for the rest). A segment over 255 bytes and an output path of
  260 characters or more are problems (errors under `fail_on_problems`). The `.md` suffix and `exclude_file_names` are
  matched without regard to case.
- The tree of the guides is data of the project and is read defensively. A symbolic link (a file, a directory, a
  cycle) in `guides_dir` or in `public/` is never followed: it is skipped with a problem (an error under
  `fail_on_problems`). A walk stops at 32 levels and at 100,000 entries, with a problem. Hidden entries of `public/` are
  not copied, as in the locale directories. A generated page and an output file are never written through a link
  (`BuildError`); `output_dir` may not be `guides_dir` or `project_dir`, hold them, or overlap `sources_dir`
  (below `guides_dir` is the default layout and stays allowed). A page is generated only if its front matter says
  `generated: true` or the first line after the front matter is the notice: a page that quotes the notice further down
  is never overwritten or removed. A heading whose id is one the theme uses for its own elements (`content`, `sidebar`,
  `search`, `main`, ...) is a problem; `{#another-id}` renames it. An option or a key of `site.lua` that is not on
  the list is refused (`ArgumentError` with `context.argument`, `ConfigurationError` with `context.field`), naming the
  replacement of an old name.
- `fail_on_problems` raises one `BuildError` listing every problem of the build, the licences page and the code
  reference, after the site is written. `\` is a separator in every path option; a drive-relative path (`C:file`) is refused
  on Windows.

The website of the framework is two trees, `website/user/` and `website/maintainer/`, each built by the plain builder into its
own site (`dist/user`, `dist/maintainer`; `/` redirects to the user site). The classification of the pages is in
[website-audience-classification.md](../reviews/website-audience-classification.md). The bootstrap runner `--internals-into <tree>` splits the generated code reference (public symbols into the built tree,
`*.internal` modules and non-public classes into the other one, `audience_locale_dirs` of `reference_site.run`). One
`site.lua` serves both trees: the `audience` option of `build` and `Site` (`--audience` of the runner) puts the name of the
tree before `{path}` in the edit link of hand-written pages, the same rule that `generate_project_documentation` applies to
each audience ([OQ-146](../open-questions.md)). The task `gen-maintainer-docs` publishes `docs/architecture/`, the ADRs, `docs/reviews/`, `docs/roadmap.md` and
`docs/open-questions.md` as generated pages of the maintainer tree (owner decision, OQ-144). There is no `check-audience`
gate: the tree is the label.

There is no HTTP API reference: the generator never renders routes or the contract. The Lua **code reference**
(modules, classes and functions of the project's `package_name`, from LuaLS annotations) is a different thing and
is generated. The OpenAPI contract is the external documentation of the HTTP API:
`openapi` serves it (`/openapi.json`) and `hecate contract export` writes it. A viewer for
it (Swagger UI, for example) is the wiring of the user, such as a Docker compose file
([OQ-135](../open-questions.md), [OQ-141](../open-questions.md), owner decision of
2026-11-17; [ADR 0012](../adr/0012-website-generator.md), amended 2026-11-19). `hecate.doc` neither renders the contract nor ships a viewer.
