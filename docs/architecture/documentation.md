# Documentation

Status: specification; [ADR 0012](../adr/0012-website-generator.md) (Accepted: site generated by
`hecate.doc` with an MDN-like theme),
[ADR 0022](../adr/0022-doc-dependencies.md) (Accepted: dependencies of the generator),
[ADR 0013](../adr/0013-english-code-multilingual-documentation.md) (Accepted).

## Two kinds of documentation

1. **Engineering documentation** (`docs/`): for contributors and agents. English only.
2. **Public website** (`website/`): for users. English source, translated.

Hosted at <https://hecate.theandre.dev> (provisional domain), deployed from `main` by
`website.yml`.

## Website structure (Diátaxis)

| Section | Purpose | Examples |
|---|---|---|
| Tutorials | learning by doing, reproducible verbatim | "Your first API", "A CRUD API with PostgreSQL" |
| How-to guides | solving one task | "Paginate a collection", "Deploy with Docker", "Add JWT authentication" |
| Reference | exhaustive, mostly generated | every package, class, function, CLI command, configuration key, error code |
| Explanation | concepts and rationale | concurrency model, suspension points, object model, data mapper, contracts |

Plus: migration guides between minor versions, glossary (public version of
`docs/glossary.md`), correspondence tables (relational algebra ↔ SQL; Hecate ↔ FastAPI /
Symfony / Express vocabulary), changelog, compatibility matrix.

The full site map is in [`website/OUTLINE.md`](../../website/OUTLINE.md).

## Generated reference

- Source: LuaLS annotations (`lua-language-server --doc` export, JSON) + route, schema
  and configuration metadata from the packages.
- Produced by `hecate doc` (Phase 3; the scripts of `packages/doc/bin/` before that, wrapped by `gen-reference`) into
  `website/en/reference/` as Markdown. Generated pages are never edited by hand; they
  carry a header comment saying so.
- The error codes page (`reference/error-codes.md`, every error class of ADR 0018 with its code, parent and
  `context.reason` values) and the configuration keys page (`reference/configuration-keys.md`) are produced by the
  `gen-error-codes` and `gen-config-reference` tasks (automation.md), from the sources read as files; like the code
  reference they are git-ignored and generated by `website.yml` before the site build.
- Translations of generated pages translate only the prose parts (summaries,
  descriptions) through translation files keyed by symbol, not whole pages.

## Theme

One original Hecate theme for the website and for user projects (ADR 0012): MIT-licensed,
light and dark modes, WCAG 2.2 AA. No code or assets from Lua Web Docs (Tailwind UI
licence).

Owner direction of 2026-10-13 (ADR 0012): `hecate.doc` is our own Lua 5.5
generator with a VitePress-like presentation and strict respect of the Hecate brand kit
(`tokens.json`, logo lockups, STIX Two / Fira Sans / Fira Code, nearly square corners, no
gradients or glows, the name never capitalised, earth as the single accent). Page chrome:

- top bar: logo, section links, search, locale switch, theme toggle, repository link,
  menu button on small screens;
- left sidebar (computed from the page tree or configured per section) and a right-hand
  "On this page" outline;
- previous/next cards, edit-this-page link, last-updated date, "written for hecate x.y and
  Lua 5.5" line;
- callouts (the five GFM alerts NOTE, TIP, IMPORTANT, WARNING and CAUTION), code blocks with a language label
  and a copy button, tables, task lists;
- search: one JSON index per locale, queried by about 150 lines of vanilla JavaScript;
- diagrams: a fenced block whose info string is `mermaid` stays a code block, and on a page that holds one the
  theme loads a vendored copy of `mermaid.js` (no CDN) that draws it in the reader's browser, in the brand
  colours of the light or the dark theme ([ADR 0033](../adr/0033-vendored-browser-libraries.md), `Proposed`;
  OQ-128). The library and its initialiser are loaded, and written to the output, only for pages with a diagram;
  without JavaScript the source stays readable.

Implementation and conventions: [`packages/doc`](../../packages/doc/README.md); open
choices OQ-33 to OQ-38. Build: `lua packages/doc/bin/build.lua website --strict` (bootstrap
runner until `hecate doc build`).

### Manual check on a narrow viewport

Before changing the navigation of the theme, build the site and open it in a browser at 375 px
wide (device mode). With the sidebar open ("Menu" in the local bar) and with the header panel open
(hamburger): a long menu scrolls inside its own container, the page behind does not move, and the
last entry is reachable with the address bar visible. `ThemeTest` guards the CSS and script rules
behind this behaviour.

## Reference page template (MDN-like)

Inspired by Lua Web Docs (<https://luadocs.com>, "like MDN, but for Lua"). Every
reference page for a class or function follows the same sections, in this order:

1. One-sentence summary.
2. Syntax (signature, LuaLS-style types).
3. Parameters and return values (including `nil` for expected absence, ADR 0018).
4. Errors raised (classes and codes).
5. Whether it may suspend (`---@async`) and on which operations.
6. Examples (tested files, runnable when possible).
7. Specifications and standards implemented (RFC sections).
8. Compatibility: Hecate version introduced, Lua versions supported.
9. See also.

## Runnable examples (WebAssembly, OQ-11 and OQ-39)

Pure-Lua packages (`core`, `schema`, `router`, `query`) could run in the browser if Lua
5.5 is compiled to WebAssembly, letting readers edit and run examples on the page.
Anything depending on the reactor (libuv) cannot run in the browser and keeps static,
tested examples. The OQ-11 spike decides.

## Content conventions (owner decision 2026-10-13, OQ-35)

- **Page title.** The title of a page is the single `#` heading of its body. That keeps the
  Markdown readable on GitHub and satisfies markdownlint MD025 and MD041. The generator
  renders that heading as the page's only `<h1>` and does not repeat it.
- **Front matter `title`** is optional and overrides only the label used in navigation,
  previous/next cards, search results and the HTML `<title>` (short label, SEO wording). It
  never replaces the visible heading. Without a body heading, `title` is displayed as the
  heading; without both, the page id is humanised and a problem is reported.
- **Code samples** are included from tested files from the start (rule below), never typed
  into the page.
- **Reference generation.** Every module table carries a `---@class` annotation so that the
  `lua-language-server --doc` export contains its functions; `hecate.doc` does not parse
  annotations itself. Parameters and returns are described in the standard form
  `---@param name type description` and `---@return type name description`.

## Dependencies of the generator

Owner decision 2026-10-13 ([ADR 0012](../adr/0012-website-generator.md)): Markdown (complete
GitHub Flavoured Markdown) and syntax highlighting come from third-party Lua, C or Rust dependencies rather than from code written in the
package; the site must remain deployable as static files on GitHub Pages. The candidates
were measured in the spike [OQ-39](../spikes/OQ-39-doc-dependencies.md); the decision is
ADR 0022 (Accepted).

## Writing rules

- Every page states the Hecate version it was written for and the Lua version.
- Every code sample is a tested file under `packages/<name>/examples/` or
  `examples/`, included by reference, so samples cannot rot. The renderer has no include
  mechanism yet: a page writes `<!-- example: packages/<name>/examples/<file>.lua -->` on a line of
  its own, then a fenced block holding the exact content of that file, and `check-docs-examples`
  fails when the block differs or the file is missing. A snippet of a few lines may stay inline.
- Vocabulary from the glossary; first occurrence of a term links to the glossary.
- Short sentences, active voice, second person in tutorials and how-tos.
- Follow the writing style below.

## Writing style

Owner decision, 2026-11-13. The public pages are written after the manner of *Programming in Lua* (Roberto
Ierusalimschy): a patient teacher who introduces one thing at a time, shows it at once, and never trades accuracy for
ease. Readability comes from the order and the pace of the text, not from looser words. The rules apply to every page
of `website/en/`; the engineering documents of `docs/` keep their denser, reference style.

1. **One idea per paragraph.** A paragraph states one idea and stops. When a paragraph needs "also", "in addition" or
   a second topic sentence, split it. Three to five sentences is a good length; a one-sentence paragraph is fine.
2. **Example right after the concept.** Each new concept is followed at once by a short example: a few lines inline,
   or a tested example file (`<!-- example: ... -->`). The example comes before the details, the options and the
   exceptions, which follow it. Never pile several concepts up before the first example.
3. **Recall a term the first time a page uses it.** The first occurrence of a glossary term on a page links to the
   glossary and is followed by a brief reminder of what it means, in a clause or a short sentence ("a filter, an
   object that wraps the action of a route, ..."). Do not assume the reader came from another page.
4. **Short sentences, lower density.** Aim for sentences under about 25 words. One clause per idea; prefer two
   sentences to a semicolon. Lists of more than three items become a bulleted list or a table. Leave room: a page
   that covers less, clearly, is better than one that covers everything in packed sentences.
5. **The precise term and the exact claim, always.** A simpler sentence never replaces a glossary term by a vaguer
   word, never drops a condition that makes the claim true ("at boot", "on the same reactor", "since 0.x"), and never
   rounds a limit or a default. When the exact claim is long, give it its own sentence or list item rather than
   simplifying it.
6. **Lead with the purpose.** A section opens with what the reader can do with the thing or why it exists, then how
   it works. Rationale and history go last, or to an explanation page.
7. **Move from the common case to the rare one.** Show the usual use first; edge cases, limits and "not available
   yet" come after, each in its own paragraph or under its own heading.

A short illustration of rules 1 to 3:

> Too dense: *Filters, composed once at boot into a chain of responsibility over the action, may pass, short-circuit
> or post-process, and errors they raise go through the guard like the action's.*
>
> Readable: *A [filter](../../website/en/reference/glossary.md) wraps the action of a route: it sees the request
> before the action and the result after it. Here is the smallest filter, one that passes the request on:* (example)
> *A filter can also stop the request before the action, by returning a result without calling `next`.*

## Code examples

Owner request, 2026-11-12. Two rules apply to every code example: the files under `packages/*/examples/` and
`examples/`, and the Lua blocks of the website pages.

1. **Comment width.** No line that holds a comment is longer than 80 characters, counting the indentation and any
   code before the comment. Code lines without a comment may be longer and are not broken unnaturally to fit. A
   line is exempted only when the line just above it is a comment holding `check-examples: allow-long-comment`.
   `check-examples` enforces this rule. It runs in the `docs-checks` and static-check jobs of `ci.yml`. A block that
   copies an example file (`<!-- example: ... -->`) is checked through that file.
2. **Output placement.** What a line makes the reader see is written in a `-- Prints:` block directly under that
   line, never gathered at the end of the example. The block starts with `-- Prints: <first line>` and continues
   on the comment lines `-- <next line>` that follow it. One block holds the output of one line. Only the rest of
   the printing statement may stand between the line and its block: the remaining arguments of a call that spans
   several lines, or closing lines such as `end)`. Inside a function, the block goes inside it, indented. Examples
   write through `print` only (`io.write` and `io.stdout` are refused). A server example that never returns ends
   with `-- Answers: <text>` instead.

```lua
local ok, value = schema.integer():validate(42)
print(ok, value)
-- Prints: true	42
```

The examples tests of every package run their examples through one shared runner, `tools/harness/examples.lua`. It
attributes each `print` to the line of the example that is running and fails when the output is missing, different,
gathered into another line's block, or separated from its line. A `print` inside a helper function counts at the
helper's line, so examples print inline. Every phase gate checks both rules on the examples of its phase
(`docs/roadmap.md`, "Phase gates").

## Translations

- Locales: `en` (source), `fr` (first), more by contribution.
- `website/<locale>/` mirrors `website/en/`.
- Each translated page records the source revision it translates (front matter
  `source_revision`); `check-translations` flags stale pages.
- Untranslated pages fall back to English with a visible notice.

## LLM-facing documentation

- `llms.txt` at the repository root is curated by hand (`gen-llms-txt` keeps its package list). The site builder
  writes `llms.txt` and `llms-full.txt` at the root of a site (llmstxt.org) only when the site configuration says
  `llms = true`; the default is off, so a project publishes nothing for language models unless it asks. `llms.txt` has
  the site title and description, then one link per published page with the `description` of its front matter,
  grouped by top-level section in navigation order (pages at the root first); `llms-full.txt` concatenates the
  Markdown of the same pages, each after a `Source:` line. Only the pages that the site publishes appear (a page of an
  audience that is not published is left out, OQ-144) and only the default locale is written. A file of `public/`
  with the same name fails the build when the key is on. The Hecate website turns it on. The output is
  deterministic.
- Every reference page has a stable anchor per symbol.

## Documentation of a project (audiences)

Documentation has two audiences, a second axis next to Diátaxis (which sorts pages by what they do
for the reader, not by who the reader is; [OQ-144](../open-questions.md), owner remarks of 2026-11-17):

- **user documentation**: build, run and operate an application on the public API, with the concepts
  and the public extension points that help to do so;
- **maintainer documentation**: change Hecate, or the project itself: architecture, ADRs, internals,
  CI and release, the reference of `*.internal` modules.

`hecate doc build` on a project produces a static site that is the project team's own documentation:
the guides the project writes, the configuration reference, and the code reference from the
project's annotations. It publishes only what it is asked to: the public output of a project is a
request (`audiences`), not a default.

- A page declares its audience in the front matter key `audience` (`user` or `maintainer`; any other
  value is a `BuildError` naming the file). The site configuration key `default_audience` (default
  `user`) is the audience of a page without the key.
- The site configuration key `audiences` lists the audiences the site publishes. Default: `{ "user" }`,
  for a project site (`hecate.doc.project.build`) and for the plain builder (`hecate.doc.build`) alike,
  so a tree without any `audience` key builds as before. The website of the framework asks for
  `{ "user", "maintainer" }` and keeps publishing everything.
- A page whose audience is not published is absent from the output, the navigation, the search index,
  the sitemap and the previous and next links. A link to it is reported like a broken link (an error
  under `--strict`). Files next to pages (images) are not filtered. A translation never publishes a
  page that the page of the default locale keeps back.
- Generated pages: the configuration reference is `maintainer`. The code reference lists public
  symbols (`user`); the pages of `*.internal` modules and of classes that LuaLS reports as `private`
  or `package` are `maintainer`, and are generated only when `audiences` includes `maintainer`. A member
  (field or method) that is `private`, `protected` or `package`, or whose name starts with `_`, is never
  listed: a member is a part of a class page, not a page.
- The configuration reference never prints the default of a secret key (`[redacted]` in its place). A
  key is a secret when its schema says `writeOnly: true` or `format: "password"`, or when the project
  lists its path in the option `secrets`: the secrets of `hecate.config` are declared at load time, not
  in the schema. When the project gives its application (`application`, a `hecate.kernel.Application`,
  duck-typed on `configuration_schema()`, so that `doc` does not depend on `kernel`), the schema of the
  configuration and the secrets declared at load time are read from it, and `secrets` adds to them; the
  explicit `configuration` schema stays for a project without a kernel application and wins.
- The third-party licences page (`project.build` option `licenses`, off by default, `maintainer` by
  default): the rocks of an installed tree read as files (name, version, declared licence, licence text,
  dependencies resolved transitively and sorted) and what the generated site bundles, with the licence
  texts of the theme. A rockspec is data: it is parsed without being run (no call, loop or loader
  accepted; an empty environment and an instruction limit for the rest), and no `luarocks` process runs.

The audience split of the website of the framework (the pages of `website/` moved or labelled) is a
separate item, and a `check-audience` gate is not written yet ([OQ-144](../open-questions.md)).

There is no API reference. The OpenAPI contract is the external documentation of the API:
`openapi` serves it (`/openapi.json`) and `hecate contract export` writes it. A viewer for
it (Swagger UI, for example) is the wiring of the user, such as a Docker compose file
([OQ-135](../open-questions.md), [OQ-141](../open-questions.md), owner decision of
2026-11-17). `hecate.doc` neither renders the contract nor ships a viewer.
