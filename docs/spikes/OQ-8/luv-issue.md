# luv issue: TCP `reuseport` (key elements, draft, not posted)

The owner decided on 2026-10-18 to open an issue first, to see whether the luv maintainers want
to add the flag themselves ([OQ-43](../../open-questions.md)). This file holds what is needed to
write it correctly. Nothing has been posted. The ready change is
[`luv-tcp-reuseport.patch`](luv-tcp-reuseport.patch) and the longer pull request text is
[`luv-pr.md`](luv-pr.md); both stay in reserve.

## The one-sentence request

`uv.tcp_bind` should accept `reuseport` in its `flags` table, as `uv.udp_bind` already does,
mapped to libuv's `UV_TCP_REUSEPORT`.

## Facts to state (each checked)

| Fact | Where it comes from |
|---|---|
| luv 1.53.0 (libuv 1.53.0) `luv_tcp_bind` reads only the field `ipv6only` of `flags`. | `src/tcp.c` on luv master, 2026-10-01 (`26e62e4`) |
| `uv.udp_bind` and `uv.udp_open` read `reuseport` (and `reuseaddr`, `linux_recverr`, `ipv6only`). | `src/udp.c`; luv PRs #796, #797, #806 (February 2026). #806 says the UDP flags "were added in 1.42.0 and 1.49.0 but went unnoticed". |
| libuv has `UV_TCP_REUSEPORT` (value 2) for `uv_tcp_bind` since 1.49.0. | libuv PR #4407 (merged 2024-05-21); `docs/src/tcp.rst` |
| libuv documents it for Linux 3.9+, DragonFlyBSD 3.6+, FreeBSD 12.0+, Solaris 11.4 and AIX 7.2.5+, and an error elsewhere. | libuv `tcp.rst`; the exact error on macOS and Windows (`UV_ENOTSUP` in the docs, a commit message says `UV_EOPNOTSUPP`) is not verified here |
| No luv issue or pull request about TCP `reuseport` exists (searched "reuseport" and "UV_TCP_REUSEPORT"; the only hits are the UDP pull request #796 and an unrelated 2019 issue #171). | GitHub search, 2026-10-18; lexical search, so absence is strong but not certain: search again just before posting |
| Passing the flag today is silently ignored, and the failure shows up late: libuv defers a bind conflict to `listen`. | reproduction below |

## Reproduction (verified on luv 1.53.0, Linux)

```lua
local uv = require("luv")
local a, b = uv.new_tcp(), uv.new_tcp()
print(a:bind("127.0.0.1", 0, { reuseport = true }))      -- 0   (flag ignored)
local port = a:getsockname().port
print(b:bind("127.0.0.1", port, { reuseport = true }))   -- 0   (the conflict is deferred)
print(a:listen(16, function() end))                       -- 0
print(b:listen(16, function() end))                       -- nil  EADDRINUSE: address already in use
```

With the patch applied, the last line prints `0`: both handles listen on the same port.

## Why it matters (the use case, in two sentences)

A multi-process server wants several processes to listen on one port with kernel load balancing
(the model of nginx's `reuseport`). From Lua that is impossible today without native code: we
had to write a small C module that calls `setsockopt` and hands the descriptor to `tcp:open`.

Evidence worth one sentence, not a table: four processes binding one port with the flag receive
evenly spread connections on Linux (largest to smallest 1.05 to 1.13), where one listening socket
shared by the processes is badly unbalanced (largest to smallest 94 to 278).

Do not oversell it. Handing accepted connections from one process to the others (Node's cluster
model) works without the flag and was as fast in our fair measurement, except above about 25 000
new connections per second per host; the flag removes that ceiling and the extra hop. Present it as
completing the binding of a libuv feature, not as a blocker.

## What to propose and what to ask

Propose: the flag in the existing `flags` table (the maintainers said they prefer one Lua
interface over `_ex` variants in #797), guarded by `LUV_UV_VERSION_GEQ(1, 49, 0)` because luv can
link an older shared libuv, with the platform note copied from libuv's documentation.

Ask, briefly:

1. Was TCP left out on purpose, or simply never done (the history suggests the latter)?
2. Is the `flags` table the interface they want?
3. On a platform where libuv does not support the flag, should luv pass the libuv error through
   (what the patch does) or ignore the flag?
4. Do they prefer to implement it themselves, or to receive a pull request? A tested patch exists
   (five lines of C, a test in `tests/test-tcp.lua` that returns early on `ENOTSUP`, and the
   `docs.md` and `meta.lua` regenerated by `docs/docgen.lua`; luv's own suite passes on Linux).

1. Run the reproduction on luv master (the line numbers and the absence of an issue may have changed).
2. Search the luv and libuv trackers once more for `reuseport`.
3. The macOS, Windows and BSD behaviour of the flag in libuv was taken from its documentation and was

   so another user cannot join an existing listener.
