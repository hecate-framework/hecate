# Spike OQ-4: TLS library and binding

Status: **partial (Linux only, time-boxed)**; decided by the owner: rustls through mlua (ADR 0021). No recommendation is final; the owner decides.

## Method

OpenSSL 3.0.13 (system headers, Ubuntu 24.04), Lua 5.5.1, GCC. Candidates cloned under
`spikes/OQ-4/` (git-ignored):

- `wahern/luaossl` (MIT, last commit 2026-09-10): built with its own makefile
  (`make all5.5 LUA_APIS=5.5 CPPFLAGS=-I/opt/lua-5.5/include`).
- `zhaozg/lua-openssl` (MIT, last commit 2026-09-20): CMake configure and a direct
  per-file compile attempted.
- Own binding to OpenSSL 3 and mbedTLS: assessed on paper only (mbedTLS is not installed
  in the environment, nothing was built).

## Findings

| Candidate | Lua 5.5.1 build | Fit with the reactor |
|---|---|---|
| luaossl | **builds unmodified**, `openssl.so` produced | TLS stream I/O is not in the Lua API: the only `SSL_new` is used by its `cqueues` integration; the library offers crypto, X.509, contexts (the `openssl.ssl.context` module) but no memory-BIO handshake and read/write calls. Driving it from luv would mean writing the missing part |
| lua-openssl | **not built** within the time-box. CMake 3.28 `find_package(Lua)` fails to locate Lua 5.5 headers even with `LUA_INCLUDE_DIR` set; a direct compile fails on `group.c`/`point.c` (`lua_State` unknown) and the `deps/lua-compat` submodule came back empty from the clone, so the failures may be a checkout problem rather than a 5.5 incompatibility (not verified) | Its sources expose `ssl` objects with `read`, `write`, `handshake`, `pending` and memory BIOs (`src/ssl.c`, `src/bio.c`), which is the shape a luv-driven TLS stream needs |
| Own binding | not built | Full control: SSL object over a memory-BIO pair, owned by the reactor (the reactor reads and writes the socket, the binding only feeds and drains BIOs); API limited to what `hecate.net` needs (client and server contexts, SNI, ALPN, verification, session reuse) |
| mbedTLS | not built | Smaller and static-linking friendly; weaker ecosystem for the certificate-store and ALPN/OCSP needs of an HTTP stack; OpenSSL is the more common choice |

Observations:

- For a luv-based runtime, a **memory-BIO design** (the TLS library never touches the
  socket) is required, regardless of candidate. Both existing bindings are general crypto
  libraries first; neither is a close fit to what `hecate.net` needs, and both carry a
  large API surface to audit (security review scope).
- Licences: all candidates MIT/Apache-style compatible (OpenSSL 3 is Apache-2.0); not a
  discriminator.

Three-platform check (throwaway workflow `spike-oq456`, PR #7, run 4, Lua 5.5.1 built from the official tarball): the llhttp and yyjson C modules, and the `mlua` modules (rustls handshake and round trip, serde_json, sonic-rs, simd-json), build and pass a smoke test on **Linux, macOS (arm64) and Windows (MSVC)**. Needed fixes, now known for the real build: macOS Rust cdylib modules need `-C link-arg=-undefined -C link-arg=dynamic_lookup`; Windows needs the Lua import library named and located for `mlua-sys` (`LUA_LIB_NAME=lua55`, `LUA_LIB`, `LUA_INC`) and explicit `__declspec(dllexport)` on `luaopen_*` in C modules.

## Recommendation

Provisional: write a small own binding to OpenSSL 3 using memory BIOs (about the size of
the OQ-6 binding, plus certificate and verification handling), and keep lua-openssl as a
reference. This needs the owner's decision and an ADR (the dependency on OpenSSL itself
is one either way).

## Addendum: Rust (mlua + rustls) instead of C

The owner asked whether a memory-safe Rust library with a Lua binding is an easy option,
given the cost and memory-safety risk of writing C. Prototype in
`spikes/OQ-4/rust-tls/` (throwaway):

- `mlua` 0.12.2 (MIT) has a `lua55` feature; `rustls` 0.23.45 (Apache-2.0/MIT/ISC) with the
  `ring` crypto provider. rustc 1.97.
- A 70-line cdylib exposes `selftest(payload)` to Lua 5.5.1: it runs a full **in-memory
  TLS 1.3 client/server handshake** (certificate generated by `rcgen`, verified by the
  client) and one application-data round trip, then returns the payload. Result:
  `hello from Lua 5.5`, handshake in 2 flights, about 0.5 ms per handshake in process.
- `rustls` is sans-IO by construction (`read_tls` / `write_tls` move bytes the caller
  provides): exactly the memory-BIO design that `hecate.net` needs, with no unsafe code
  written by us for the protocol part. Memory safety is a property of the TLS code, and
  of the `mlua` boundary.
- The resulting `.so` is 2.8 MB, links no OpenSSL (`ldd`: none), 43 crates in the normal
  dependency tree (the prototype includes `rcgen` for the test; a client/server library
  without it is smaller).
- Costs: a Rust toolchain becomes a build requirement for contributors and for anyone
  building the rock from source (LuaRocks has a `rust-mlua` build type, not tried here);
  `ring` still compiles C and assembly, so a C compiler stays required; one more language
  in the repository (ADR needed, owner gate); the Lua C API boundary is handled by `mlua`
  (unsafe inside `mlua`, not in our code). Binary releases (self-contained CLI, OQ-13)
  can link a Rust static library.
- Not checked: macOS and Windows builds (rustls and ring support both; expected to work),
  ALPN and SNI, client certificates, session resumption, performance under load, crates
  supply-chain policy (`cargo-deny` in `check-licenses`).
- Not covered by rustls: some OpenSSL features (legacy algorithms, PKCS#11, FIPS via
  aws-lc-rs only). Probably irrelevant for a web framework.

Updated comparison for the owner's criteria (speed, work, memory safety):

| Option | Work | Memory-safety exposure | Notes |
|---|---|---|---|
| Own C binding over OpenSSL BIOs | medium to high | highest (we write the C) | smallest toolchain change |
| Lua-only TLS | not viable | n/a | TLS in pure Lua would be both slow (cryptography) and risky |
| **Rust: mlua + rustls** | low to medium (small binding) | lowest | adds Rust to the toolchain |
| luaossl / lua-openssl | low | OpenSSL C code in a general binding | no suitable I/O API / not built |

Revised recommendation: **rustls through `mlua`** is the better fit than a hand-written C
binding, if the owner accepts Rust as a build-time tool for native modules (scope:
`net` TLS only, with the toolchain pinned in the bootstrap). Fallback: own C binding.

## Status of the open items after the decision (ADR 0021)

The owner chose `rustls` through `mlua`, so the items that compared other candidates are
closed without being done: building lua-openssl, prototyping an own OpenSSL binding over
BIO pairs, and the mbedTLS build and size comparison.

macOS and Windows build of the chosen stack: done (three-platform check above).

Carried over to the `net` implementation, to be settled there and not before:

- ALPN, SNI, client certificates, session resumption, and the certificate-verification
  defaults (platform trust store versus bundled roots).
- Crypto provider: `ring` (used here) or `aws-lc-rs`.
- Static linking of the Rust module into the self-contained executable (OQ-13, still open).
- Performance under load of the TLS path on the reactor.
- A LuaRocks `rust-mlua` build, prebuilt binaries, `cargo-deny` and `cargo audit` in CI.
